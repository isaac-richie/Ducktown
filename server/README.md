# Ducktown local backend

Run `npm install` and `npm start` from the project root, then open `http://127.0.0.1:8787/`. `npm start` builds the source in `frontend/` before the loopback server starts; the server serves `dist/frontend/` when available and falls back to the previous `outputs/` preview otherwise. For hot reload, keep the backend running and open `http://127.0.0.1:5173/` after `npm run dev:frontend`. Override the backend port with `DUCKTOWN_PORT`. Run tests with `npm test`.

The active database is `data/ducktown.json.sqlite` (SQLite, WAL mode, full synchronous commits, mode 0600). On first start, existing `data/ducktown.json` content is imported once and left in place as a legacy source. Subsequent writes go only to SQLite; the JSON file will not reflect new accounts or posts. State changes use an immediate SQLite transaction, and each API request refreshes the current committed state. The application document remains one SQLite record, so this is a durable local beta store, not a horizontally scalable public database. Run `npm run backup:db` for a consistent SQLite backup under `data/backups/`. Run `npm run rehearse:restore -- /absolute/path/to/BACKUP.sqlite` to copy a backup into a temporary directory, check SQLite integrity and account/profile links, boot the restored app on an ephemeral loopback port, and compare its feed with the backed-up state. This rehearsal never overwrites the source or live database. Stop the app before a real restore, and keep database files and backups private because they contain password hashes and session hashes.

API v1:

- `GET /api/v1/health` — local demo status, never a hardware status claim.
- `GET /api/v1/robots/:id` — public simulation robot profile (Pepper remains an unowned demo).
- `GET /api/v1/behaviors` — six illustrative catalog summaries.
- `GET /api/v1/posts` — public feed, including clearly labeled legacy demo notes.
- `GET /api/v1/auth/me` — current account and owned simulation duck, or null.
- `POST /api/v1/auth/register` — JSON `{ "handle": "...", "password": "..." }`; creates an account and one simulation-only duck.
- `POST /api/v1/auth/login`, `POST /api/v1/auth/logout` — session lifecycle.
- `POST /api/v1/auth/recover` — reset with the one-time recovery code shown at registration, revoke every session, rotate the code. `POST /api/v1/auth/recovery-code` makes a replacement code after checking the signed-in user's password. Recovery attempts are limited per handle.
- `GET /api/v1/profiles`, `GET /api/v1/profiles/:handle`, `PUT /api/v1/profile` — discover and edit simulation duck profiles. Hidden profiles are accessible only to their owner; Pond posts stay public.
- `PUT|DELETE /api/v1/profiles/:handle/follow` — follow or unfollow a visible duck.
- `GET /api/v1/following` — private list of followed ducks, including a minimal handle for profiles that later became hidden so they can still be unfollowed.
- `GET /api/v1/saves`, `PUT|DELETE /api/v1/saves/:kind/:id` — account-bound saved posts, Workshop ideas, and creative prompts.
- `GET /api/v1/notifications`, `POST /api/v1/notifications/read` — private follow/reply news.
- `POST /api/v1/posts` — authenticated JSON `{ "text": "...", "robotId": "optional owned id" }`, 1–800 characters. The server checks robot ownership.
- `PUT|DELETE /api/v1/posts/:id/like` — signed-in, idempotent like or unlike. Counts and viewer state come from the local server, not browser storage.
- `GET /api/v1/posts/:id/replies`, `POST /api/v1/posts/:id/replies` — public human replies, with signed-in 1–400 character posting. Sample demo-story reply counts remain illustrative and cannot receive real replies.
- `POST /api/v1/posts/:id/report`, `POST /api/v1/replies/:id/report` — signed-in reports with fixed reasons. A local operator can inspect reports and hide or restore posts/replies using `node server/moderate.js --list`, `--hide POST_ID`, `--restore POST_ID`, `--hide-reply REPLY_ID`, or `--restore-reply REPLY_ID`. Hidden posts leave the feed; hidden replies leave the conversation and its visible count. A report alone never hides content.
- `GET /api/v1/simulator/status|health|policies|version|realtime` — authenticated, read-only observer of Pollen’s documented `scripts/duck-sim` CLI. No command accepts user-supplied arguments.
- `GET /api/v1/installed-policies` — authenticated, live structured view of SDK-reported policy slots, skills, and built-in actions. It does not imply a policy ran.
- `GET /api/v1/sdk-observations` — current account’s private observation history.
- `POST /api/v1/sdk-observations` — explicitly invoke all five read-only checks and save an observation only if each succeeds. No client-provided policy IDs, scores, or telemetry are accepted.
- `GET /api/v1/receipts` — signed-in account's private, operator-assigned simulator evidence summaries. Never returns the raw telemetry and never publishes to the feed.
- `POST /api/v1/receipts/:id/share` — explicit owner action with JSON `{}`. In one store mutation, publishes a server-written, conservatively labeled simulator observation and marks its private receipt shared. It refuses custom result claims and duplicate publishing; raw telemetry stays private.

## Official simulator observer

The observer is disabled until `DUCKTOWN_MICRODUCK_ROOT` points to an official `pollen-robotics/microduck` checkout containing executable `scripts/duck-sim`. Start Ducktown with that environment variable, then sign in and use Human Perch → “Check simulator status,” or open Workshop for the SDK-reported installed-policy list. Ducktown does **not** install, start, stop, drive, update, load policies, access the camera, or connect to hardware. It executes only these allowlisted read-only commands, without a shell: `status`, `ctl health --json`, `ctl policy list --json`, `ctl version`, and `realtime`. Observation responses preserve raw CLI output; the installed-policy view parses only the policy-list JSON. Neither is a verified run receipt. An absent checkout yields a visible “not configured” result.

This follows Pollen’s [simulator guide](https://github.com/pollen-robotics/microduck/blob/main/docs/robot/simulation.md) and [robotctl cheat sheet](https://github.com/pollen-robotics/microduck/blob/main/docs/robot/cheatsheet.md). The simulator guide says the daemon-backed sim uses the same control loop, policies, IPC, and `robotctl` as the robot, but does not model hardware drivers. Ducktown therefore cannot infer hardware behavior or robot-safe performance from these checks.

An observation records the raw policy-list and version text, the check times, and SHA-256 hashes of each CLI output. It is account-private, capped at 20 records per account, and always marked `verification: unverified`, `isRun: false`, `hardwareConnected: false`. A hash detects changed output; it is **not** an attestation from Pollen or proof that a policy ran. No observation is saved unless every check succeeds. The simulator must already be running under the official setup; Ducktown never starts it.

This is a **local beta backend**, not an Internet-ready service. Passwords are scrypt-hashed; random sessions are stored by token hash and sent in HttpOnly, SameSite=Strict cookies. Writes are same-origin and owner-scoped. Recovery codes and local report review exist. The browser still cannot start simulator jobs; the fixed skill workflow below is operator-only. Do not expose port 8787 beyond loopback. Content from the API is escaped by the frontend before display. Browser-only demo drafts remain in localStorage and are not automatically uploaded or assigned to an account. No API endpoint creates verified simulator or hardware evidence.

For a future HTTPS deployment, set `DUCKTOWN_PUBLIC_ORIGIN` to the exact external origin, such as `https://town.example`. Startup rejects HTTP origins and origins with paths. This mode requires the external `Host` and an exact `Origin` on browser writes, sets `Secure` on session cookies, and emits HSTS. The server still binds to `127.0.0.1`; a reverse proxy must terminate HTTPS, preserve the external Host, block direct public access to port 8787 and `/api/v1/operator/*`, and overwrite any inbound `X-Real-IP` with the actual client address. The app trusts that header only from its loopback peer; without it, anonymous limits fall back to one shared proxy-address bucket. Operator CLI calls and the local health probe use the direct loopback address; operator routes are rejected through the public Host. Do not set this mode on the current plain-HTTP local browser URL, because secure cookies cannot be sent there.

Write limits are stored in SQLite and survive restarts or a second app connection: at most 10 registrations per client address per hour, 60 login attempts and 20 recovery attempts per client address per 15 minutes, 6 Pond notes, 30 replies, 30 follow requests, 12 SDK observations, and 240 total account writes per hour; plus 10 reports, 6 receipt shares, and 30 profile edits per account per day. The existing per-handle login/recovery attempt caps remain. A rejected write returns HTTP 429 with `Retry-After`; invalid or failed actions may count toward a limit. These are baseline controls, not a substitute for proxy-level request/body limits, bot mitigation, staffed moderation, and monitoring. A copied-backup restore rehearsal and isolated desktop/mobile browser tests now pass. Public deployment still needs a rehearsal against the chosen host, operator coverage, monitoring, and a deployment decision.

The JSON observation path was validated against a running official daemon simulator on 2026-09-27. Ducktown's API matched the CLI's seven policy slots, three policy skills, and two daemon-built-in actions. A controlled stop/restart confirmed that status, health, policy list, version, and realtime checks fail closed when the daemon is down. Run `npm test` for the regular suite, then run `npm run test:live` with `DUCKTOWN_MICRODUCK_ROOT`, `DUCK_SIM_STATE`, and `DUCK_SIM_PORT` set for the isolated SDK observation test. CPU-heavy account tests can temporarily slow the simulator below its 45 Hz health floor; Ducktown then correctly saves no observation. The standalone smoke runner captures a bounded SDK telemetry window and can mark **execution observed in simulation** when the policy appears and returns cleanly. It still cannot verify task success, a ball-kick outcome, hardware safety, or an SDK completion event. Keep hardware control out of the public web process.

## Isolated local simulator run

The official checkouts live at `work/microduck` and `work/microduck_rl`; they are separate from Ducktown's own code. After `uv sync --no-dev --frozen` in the RL checkout and a successful Cargo build, start `sh work/run-official-sim.sh` from the project root. It uses `/tmp/ducktown-sim-0927` and port 17801 by default, never Pollen's normal `~/.cache/duck-sim` state or port 7801. Leave that terminal running. In another terminal, start Ducktown with `DUCKTOWN_MICRODUCK_ROOT="$PWD/work/microduck" DUCK_SIM_STATE=/tmp/ducktown-sim-0927 DUCK_SIM_PORT=17801 npm start`. Stopping the runner invokes Pollen's `duck-sim down` for that isolated state. Its status output is an SDK observation, not a safety certification or a verified run receipt.

For an explicit, simulator-only, fixed-scene one-shot smoke attempt, run `DUCK_SIM_STATE=/tmp/ducktown-sim-0927 DUCK_SIM_PORT=17801 node server/skill-smoke.js --execute`. This separate CLI checks the daemon health, standing state, real-time speed, official v5 policy source, policy/scene hashes, and SDK-reported 0.5-second `kick_left` skill. Before sending `robot do kick_left --json`, it subscribes to the official `robotctl monitor --hz 50 --json` state stream. It requires a healthy standing baseline, a sampled `kick_left` policy window, return to standing/walking policy, monotonic timestamps, no gap above 80 ms or missed control-loop ticks in capture, at least 25 skill samples per expected second, and healthy postflight. The raw monitor NDJSON, SHA-256, compact frames, and verdict are stored in a local private file under `work/evidence/`. A clean verdict is only **execution observed in simulation**, not Pollen-signed completion or measured performance. The fixed bare-floor scene has no ball-outcome metric. The CLI never runs through Ducktown's web API and never calls hardware. It uses an exclusive local lock; uncertain timeouts are not retried. A postflight failure is retained, and only the read-only health check may be retried to document recovery.

## Private receipt import (local operator only)

Start the updated Ducktown server, then sign in to an existing local account. A person operating this machine may explicitly assign one captured artifact to that account with `node server/import-receipt.js --handle HANDLE --artifact skill-smoke-UUID.json`. The CLI reads a private token stored beside the legacy JSON path and calls a loopback-only operator endpoint; browsers and normal account sessions cannot import evidence. The server reads only a basename-matched regular file under `work/evidence/`, validates the envelope and raw-trace hashes, reconstructs the policy-window verdict from every raw SDK frame, rejects duplicates and unsupported claims, and writes only a small private summary to the account's owned simulation profile. The Human Perch reads that summary through `GET /api/v1/receipts`. Import does not make a feed post. The owner must review the claim and explicitly publish it to the **local** Pond; the server fixes the public wording, labels operator attribution unverified, and publishes no raw telemetry, score, completion event, or hardware claim. Sharing is single-use and tested for ownership and duplicate attempts. The local token and hashes are **not** Pollen attestations; assigning an artifact to an account is an operator assertion, not proof that the account owned the simulator. Keep the token and evidence files private. The SQLite store and local operator path remain development-only, not Internet-ready.

## Fixed simulator challenge (local operator only)

Once the isolated official simulator and Ducktown server are both running, create the intended local account, then run `DUCK_SIM_STATE=/tmp/ducktown-sim-0927 DUCK_SIM_PORT=17801 node server/run-challenge.js --execute --handle HANDLE`. The command checks that exact account and the loopback server **before** issuing one allowlisted `kick_left` skill. It records the official monitor stream, validates the clean `stand → kick_left → stand/walk` sequence and postflight health, saves a private artifact, and attaches only a validated summary to that account. The account owner then reviews the three-step timeline in Human Perch and explicitly shares it to the Pond if desired. Failed, uncertain, or inflated attempts never attach to an account or publish; their private artifact is retained for diagnosis. No browser endpoint can start this challenge, and no physical robot is addressed.

This is an **observed move-and-return challenge**, not a successful ball-kick claim. The official daemon state stream reports policy and robot state, not ball displacement or a task score. A ball-outcome challenge needs a supported official measurement surface; Ducktown does not invent one or read private simulator internals to compensate. `DUCKTOWN_LIVE_CHALLENGE=1 DUCK_SIM_STATE=/tmp/ducktown-sim-0927 DUCK_SIM_PORT=17801 node --test server/live-challenge.integration.js` runs the same SDK path against an isolated temporary Ducktown account and database, then checks private review and explicit sharing.
